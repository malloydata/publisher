# dbt + Malloy: jaffle-shop

dbt's [jaffle-shop](https://github.com/dbt-labs/jaffle-shop) with a Malloy semantic layer over
it — and, in a second package, the same project with dbt's transformations absorbed into Malloy.
Two packages, because they are two different answers to "where does the seam go":

| Package | What it is | Reads |
|---|---|---|
| `semantic-layer/` | dbt's semantic layer converted to Malloy. **dbt untouched.** | the marts dbt built (`data/*.parquet`) |
| `transforms/` | dbt's staging + marts rebuilt in Malloy, materialized with `#@ persist` | the raw data dbt starts from |

Everything here runs with no warehouse, no credentials, and no dbt installed. DuckDB reads the
committed Parquet in place.

```bash
bun run start
# then open the `examples` environment: dbt-jaffle-shop and dbt-jaffle-shop-transforms
```

Start with [`semantic-layer/jaffle_shop.malloynb`](semantic-layer/jaffle_shop.malloynb). It states
the number dbt's own engine returns beside each Malloy query.

## The short version

**23 dbt metrics: 20 became Malloy measures and all 20 match dbt's output exactly.** Two became
views because a measure cannot hold a window. One is deferred. dbt's 27 data tests and 3 unit
tests are *not* carried over. Full accounting, with the reasons, in [COVERAGE.md](COVERAGE.md).

## `semantic-layer/`: the semantic layer over dbt's marts

This is the default and the recommended shape. dbt keeps the transformations and the tests; Malloy
becomes the layer analysts and agents query.

Two files, generated by [`tools/dbt_to_malloy.ts`](tools/dbt_to_malloy.ts) from dbt's artifacts:

- **`bindings.malloy`** — one source per dbt model, every column, with dbt's `schema.yml`
  descriptions carried over as `#(doc)`. This is the only file that names a physical table, so
  schema drift is a reviewable diff here and nowhere else.
- **`jaffle_shop.malloy`** — the semantic layer: primary keys and joins from dbt's entities,
  measures from dbt's metrics, views from dbt's saved queries. Names no dataset.

Plus **`analysis.malloy`**, hand-written, holding the two metrics that had to be views.

Regenerate, or check for drift:

```bash
# needs a built jaffle-shop: dbt build && dbt docs generate
bun run tools/dbt_to_malloy.ts --target /path/to/jaffle-shop/target
bun run tools/dbt_to_malloy.ts --target /path/to/jaffle-shop/target --check   # non-zero on drift
```

The generator reports what it could not convert, and why, every time it runs.

### What the conversion actually carries

- **Documentation.** Every dbt model and column description becomes a `#(doc)`, so it reaches the
  Explorer UI and any agent reading the model over MCP. Authored once in `schema.yml`.
- **Joins with declared cardinality.** dbt entities name their own targets: a `foreign` entity
  matches the model whose `primary` entity has the same name. No join-key guessing.
- **Metric definitions, including the awkward ones.** Filtered metrics, ratios, and derived
  metrics whose inputs span two models — `order_gross_profit` subtracts a cost living on `orders`
  from revenue living on `order_items`, across a one-to-many join, and matches dbt to the cent.
- **The questions people ask.** dbt's three `saved_queries` became views.

## `transforms/`: the same project with dbt's transforms absorbed

The other end of the seam. `staging.malloy` and `marts.malloy` rebuild dbt's six staging models
and six marts in Malloy, reading the raw data, with `#@ persist` where dbt would write a table.

What dbt expresses as a `+materialized: table` config plus a model file is one annotation:

```malloy
#@ persist name="orders"
source: orders is stg_orders extend { ... } -> { ... }
```

Including the part that looks like it needs SQL — dbt's `orders.sql` closes with
`row_number() over (partition by customer_id order by ordered_at)`, which is a `calculate:` in
Malloy.

A standalone Publisher does not build on publish. Trigger it:

```bash
malloy-pub materialize --environment examples --package dbt-jaffle-shop-transforms --wait
```

All six marts build (`COPY`, 1–23ms each on this sample) and queries then read the built tables.

**This package is a demonstration, not a recommendation.** It rebuilds tested marts, and the tests
do not come with them. Read [COVERAGE.md](COVERAGE.md) § Layer C for the three real differences
from dbt's output — floating-point money, a differently-constructed surrogate key, and 77 itemless
orders that dbt records as NULL and Malloy as 0.

## The data

`dbt build` was run on a deterministic 150-customer sample of jaffle-shop, and its output
committed as Parquet: 9,568 orders and 14,250 order items over 12 months (2024-09-01 to
2025-08-31), so the month-over-month and cumulative metrics have something real to say. The full
jafgen dataset is ~16MB of CSV; this is ~1.6MB of Parquet. `dbt build` is green on the sample: 43
passed, all 27 data tests and 3 unit tests included.

`semantic-layer/data/` holds the marts dbt built. `transforms/data/` holds the raw inputs dbt
started from. `tools/semantic_manifest.json` is dbt's semantic manifest, committed as a readable
reference for what the converter reads — the entities, dimensions, metrics, and saved queries that
became the model above. Regenerating the Malloy needs a *built* dbt project, because the converter
also reads `manifest.json` (descriptions) and `catalog.json` (the column schema), and those are
left out here rather than vendoring a megabyte of JSON.

## Doing this to your own dbt project

Read the [`malloy-dbt-review`](../../skills/malloy-dbt-review/SKILL.md) skill. It covers reading
the artifacts, the two naming collisions that bite on every real project, which metric types

wrote yourself.
