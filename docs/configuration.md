# Configuration

> What this is: the complete runtime configuration reference — the config file, every environment
> variable and CLI flag, the OOM/operational-tuning knobs, and the metrics that observe them. For how
> to _run_ the server, see [deployment.md](deployment.md).

Publisher reads its runtime configuration from `publisher.config.json` and a handful of environment
variables. Every CLI flag below has an env-var equivalent; pass either.

## Bring your own config

Pass `--config <path>` to point the server at a specific `publisher.config.json`, or place a
`publisher.config.json` in the directory you launch from. Both forms override the bundled default.

```bash
# Point at a directory that holds your own publisher.config.json + packages
npx @malloy-publisher/server --port 4000 --config /path/to/your/publisher.config.json

# Or cd into that directory and rely on the implicit lookup
cd /path/to/your/project && npx @malloy-publisher/server --port 4000
```

Your packages can live anywhere; they do not have to be inside this repo. A package `location` may be
absolute, start with `~/`, or be relative to the directory holding the config it appears in. Keeping
a config next to the packages it points at means the two move together, which is what makes the
config worth committing:

```
my-data/
  publisher.config.json
  sales/                    # your package: publisher.json + sales.malloy
```

```json
{
  "environments": [
    {
      "name": "local",
      "packages": [{ "name": "sales", "location": "./sales" }]
    }
  ]
}
```

The package directory format itself (`publisher.json` fields, models, data files) is documented in
[packages.md](packages.md).

Do not author packages under `publisher_data/`. That is storage Publisher manages for itself: it
copies each configured package in (or symlinks it, under `--watch-env`), and `--init` deletes the
whole tree.

The copy is the part that surprises people: **without `--watch-env`, a local package is served
from its boot-time copy, so edits to your source directory are never read**, however many times
you save or reload — a `?reload=true` still answers 200, recompiled from the copy. Local authoring
means starting the server with `--watch-env <env>`, which mounts the environment's local packages
in place and live-reloads them.

Adding `--watch-env` to a _later_ boot is not enough on its own, and this is the one to watch for:
the mount is decided when an environment is first loaded from config, so a package already copied
into `publisher_data/` stays a copy, and the boot still logs `Watch mode active` over it. Pass
`--watch-env <env> --init` once to re-mount (`--init` alone re-copies). After that, plain
`--watch-env` boots keep watching. `publisher_data/<env>/<pkg>` shows which you got: a symlink is
mounted, a real directory is a copy.

A `location` can also be a `https://github.com/...`, `gs://`, or `s3://` URL, which Publisher
downloads. Only local directories are eligible for `--watch-env`.

To add a BigQuery-backed sample (`bigquery-hackernews`) alongside the bundled examples, copy
[`packages/server/publisher.config.example.bigquery.json`](../packages/server/publisher.config.example.bigquery.json)
over your `publisher.config.json` and set `GOOGLE_APPLICATION_CREDENTIALS`. For the database
connection reference (BigQuery, Snowflake, Postgres, DuckDB, and more), see
[connections.md](connections.md).

### Where to put these

Publisher reads them from its environment, and Bun loads a `.env` file from the directory you
start the server in, so a local setup is one file and no flags:

```
# .env
EMBEDDING_API_KEY=sk-...
EMBEDDING_DIMENSIONS=768
```

`.env` is gitignored. [`.env.example`](../.env.example) at the repo root lists the semantic-retrieval
variables with their defaults; copy it to `.env` and fill in the key.

A string anywhere in `publisher.config.json` may also reference an environment variable as
`${VARNAME}`, which is how a warehouse password or an SSH private key stays out of a file that
is usually committed:

```json
"postgresConnection": { "password": "${PGPASSWORD}" }
```

One thing to know before relying on it: the substitution happens when the config file is
_read_, which is the first boot on a fresh server root or any boot with `--init` — a normal
boot loads the persisted copy and never sees the file.

A variable that is not set, like any config Publisher cannot parse, is a startup error. The
server prints `PUBLISHER_INIT_FAILED` naming the file, the variable and the remedy, and does
not begin serving:

```
PUBLISHER_INIT_FAILED error="Could not read publisher.config.json: Environment variable
'${TYPOD_NAME}' is not set in configuration file. Fix the file, or move it aside to fall
back to the bundled default."
```

A config file that is simply **absent** is not an error — Publisher falls back to its bundled
default.

`PUBLISHER_MAX_RESPONSE_BYTES` measures the shape the caller asked for, not one fixed shape.
On the model-query endpoint that means two requests differing only in `compactJson` reach the
cap at different result sizes. Over MCP it measures the compact rows the tool's envelope is
built from, which is not what the agent receives: the envelope is capped separately at 90k
characters by its own budget.

PostgreSQL and other database-specific connections may also honor their respective driver env vars
(e.g. `PGSSLMODE`).

### The `.mcp.json` the server writes

On startup the server writes a `.mcp.json` into the directory it was run in, naming the MCP endpoint it
actually bound, so an agent started in that directory finds the Malloy tools with no registration
step. This is the one place these rules are written down; the README, `AGENTS.md` and
[deployment.md](deployment.md) point here rather than repeating them.

It lands in the **working** directory, not `--server_root`, because the file is for whoever opens an
agent there. It only ever creates, and never reads: an existing file may hold other servers and their
credentials, and rewriting it on every boot would churn version-controlled files.

It does not always write one. Whenever it does not, it says so at `info` and prints the `claude mcp add`
command that connects an agent anyway, so the startup log is the authority rather than this list. The one
exception is turning it off with `PUBLISHER_NO_MCP_CONFIG` or `--no-mcp-config`, which is deliberately
silent: you asked for nothing, so it says nothing. Everything below is announced.

| Case                                                         | Why                                                                                                                                                                              |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The directory already has a `.mcp.json`                      | Only ever created, never edited. Yours is left exactly as it is, unread.                                                                                                         |
| The directory is inside a git working tree                   | An untracked file in a checkout is a surprise in `git status` and gets committed by accident. Your own project is usually a repo, so this is the common case, not an exotic one. |
| The directory is your home directory, or the filesystem root | Nobody opens an agent in either, and a process manager that leaves the working directory unset lands in `/`.                                                                     |
| The MCP port bound is not the one requested                  | `--mcp_port 0`, or a non-numeric `MCP_PORT` under Bun (Node refuses to bind at all). That port changes every run, so a saved file would be wrong from the next boot.             |
| The write failed                                             | For instance a read-only directory. Nothing is broken: the server is serving, only the convenience file is missing.                                                              |

The command it prints uses the default local scope, which is the scope that outranks a project
`.mcp.json`. `-s user` would be shadowed by the very file that caused the message.

The URL names the address the server bound, using the loopback literal of that family when the bind is
a wildcard, rather than `localhost`, which is ambiguous across IPv4 and IPv6. That is for correctness,
not isolation: any process running as you can bind the same port.

**The file outlives the server and is never corrected.** A stale one does not simply fail. If something
else holds that port later, perhaps a second Publisher serving different data, an agent started there
connects to it and answers from the wrong model. `list_packages` names the environment and packages
an agent is actually talking to, which is the way to settle it. That detects the accident, which is the
realistic case; it is not proof against a process deliberately holding the port, since that process can
answer too.

The Docker image sets `PUBLISHER_NO_MCP_CONFIG=1`, since no agent session starts inside a container.

## How get_context searches

Every ranked `get_context` request (a target with `search_text`) is answered by one engine, for every
package. A request with no `search_text` is a listing: it enumerates what its targets name, needs no
index and no model, and works in every state. The engine answers in four steps:

1. **Find.** For each target, ranked lists over the whole package are fused by rank: embedding closeness
   (when an embedding provider is configured), keyword match (BM25), and matches against the stored
   values of `#(index)` dimensions. The best `fcj.perTarget` candidates per target go on.
2. **List.** The judge is shown every target's best candidates (`fcj.listTopK`, plus any candidate
   ranked high in one list alone, `fcj.listUnion`), grouped by the source that owns them, and for each
   field the join routes by which another listed source reaches it (`fcj.listRoutes`). Set
   `fcj.connect` to `"clusters"` to group candidates into the few sources whose joins explain the
   targets together, one judge call per group.
3. **Judge.** One chat model call per request picks, for each target, which candidates to return, and
   names the caveats it applied. With no LLM configured, or `fcj.judge: false`, each target gets its
   best few candidates and the call is skipped.
4. **Respond.** The picks are returned as source cards with their fields nested in them. Beside
   `sources` the response carries `clusters` (the sources one query can combine, with what each
   answers), `coverage` (target by cluster, when there is more than one), `unresolved_targets` and
   `engine: "fcj"`. An answer longer than one page carries `next_offset`; call again with the same
   arguments and that `offset` for the next page of the same result (held for 10 minutes).

The engine builds its own index when a package loads (and on reload): a catalog of the package, search
text for each field, a keyword index, a value index of `#(index)` dimensions and the embedding vectors.
It is built in the background, one package at a time across the whole server, because the embedding
provider and its rate limit are shared. A reload does not repeat work: every model call and every
embedding is stored by content, so a package that changed nothing costs none. A source marked
`#(agent-hidden)` (or defined in a file marked `##(agent-hidden)`) gets no card of its own; its
fields are reached through the joins of the sources that are served.

### Embeddings

`EMBEDDING_API_KEY` (or `retrieval.embedding` in `publisher.config.json`) turns the closeness list on, so
synonyms and `snake_case` names match by meaning (`departure delay` finds `dep_delay`). Without it,
keyword and value matching still run, so a query only matches entities that share words with it.

What to know before turning it on:

- What leaves the machine: for each field, its name, its `#(doc)` text and the sentences derived from
  them; the values of `#(index)` dimensions on ungated sources (`fcj.valueEmbeddings: false` stops
  that); and the query strings agents pass to `get_context`. Model source code, other data and query
  results are never sent. Point `EMBEDDING_API_BASE` at a local OpenAI-compatible server (Ollama, vLLM)
  to keep everything on the machine; with a local server also set `EMBEDDING_MODEL` to a model that
  server actually serves, since the default names an OpenAI model.
- Storage: vectors are stored in the server's own `publisher.db`, keyed by a content hash, so only new
  or changed text is embedded, across restarts too. `--init` wipes them with the rest of persisted
  storage; the only cost of a wipe is embedding again.
- When indexing starts: when a package loads, at boot, on add or install, and on reload, without waiting
  for a question. Each batch of up to 256 rows is saved as it returns, so a failure part-way keeps what
  was saved. A 429, a 5xx or a timeout is retried up to five times with exponential backoff and jitter,
  honouring `Retry-After`; a rejected key or another 4xx fails at once. A failed build is tried again by
  the next question after a 60 second cool-down.
- What a search returns while the index is building: a normal result (not an error) with empty
  `sources`, `retrieval: "indexing"` and a warning that says to ask again in a few seconds. A listing
  works now. When the query text cannot be embedded, or the build cannot finish, the response is an
  error whose `retrieval_reason` (`provider-error`, `unavailable`) says why. A server with an embedding
  provider never answers with a ranking that differs from the finished index's.
- Checking readiness without watching the log: `GET /api/v0/environments/{env}/packages/{pkg}` carries an
  `embeddingIndex` object. Its `status` is `lexical` (no embedding provider is configured: a mode, not a
  failure), `indexing`, `ready` or `error`, and its `fcj` object holds the engine's own state, including
  the build report once built and `lastError.message` after a failed build. The row and entity counts
  are `0`: the engine keeps no per-entity index to count. Poll until `ready` before measuring retrieval
  quality. After a restart every package reads `indexing` until its turn in the queue has checked its
  stored vectors, which is quick when nothing changed.
- What was removed with the earlier search: `retrieval.indexing.maxEntities` no longer does anything (the
  server logs a warning if it is set), `EMBEDDING_MIN_SIMILARITY` now applies to `search_database_schema`
  only, and a response no longer carries `below_cutoff_count` or `total_entities`. The engine has no
  similarity floor: it returns the best candidates and lets the judge decide, and a target nothing
  answers is named in `unresolved_targets`.
- To measure the engine on your own models, use the `eval-loop` skill.

### Providers and the retrieval settings

Retrieval settings live in two files with two owners, and the only environment variables are the
two API keys (plus the older `EMBEDDING_*` ones, which keep working as a fallback). The
**server operator** owns `publisher.config.json`; a **package author** owns the package's
`publisher.json`. A package can switch a feature on but never past what the operator allows: the
credentials, what may leave the machine and the spend ceilings are all in the operator's file.

`publisher.config.json`, the `retrieval` block (every key is optional):

```json
{
  "retrieval": {
    "llm": {
      "provider": "anthropic",
      "model": "<a model your provider serves>",
      "timeoutMs": 30000,
      "concurrency": 4,
      "maxCallsPerSync": 300,
      "maxCallsPerRequest": 20
    },
    "embedding": {
      "provider": "openai",
      "model": "text-embedding-3-small",
      "dimensions": 512,
      "queryPrefix": "",
      "documentPrefix": ""
    },
    "egress": { "preset": "default" }
  }
}
```

| ------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `llm.provider`                                                      | One of `openai`, `openai-compatible`, `ollama`, `anthropic`, `google`, `vertex`. Setting it is what turns LLM features on (see below). Required with `llm.model`.                                                                      |
| `llm.model`                                                         | The chat model name your provider serves. Required.                                                                                                                                                                                    |
| `llm.baseUrl`                                                       | Required for `openai-compatible`. | `dimensionValues.enabled`                                           | See "Dimension value search".                                                                                                                                                                                                          |

**Keys.** Secrets are environment variables only, never file entries: `LLM_API_KEY` for the chat
model and `EMBEDDING_API_KEY` for the embedding model (they are separate because the two are often
from different vendors with separate budgets). `ollama` needs no key. `vertex` needs none either: it
signs requests with Application Default Credentials (`gcloud auth application-default login`, or
the service account the process runs as) and the `cloud-platform` scope. A key is never logged, and
an ambient `OPENAI_API_KEY` is never read.

**Precedence.** When a key is set in the file and the matching `EMBEDDING_*` variable
(`EMBEDDING_MODEL`, `EMBEDDING_API_BASE`, `EMBEDDING_DIMENSIONS`) is also set, the file wins; the
variable fills in anything the file leaves out.

**When the LLM is on.** LLM features are on if and only if `retrieval.llm.provider` is set and
either `LLM_API_KEY` is set or the provider is `ollama` or `vertex`. Otherwise they are all off and
nothing errors: the server logs a warning if a provider is named without a key, and `get_context`
answers without the judge, the index-time questions and the source summaries.

**Validation.** A bad value stops the server at startup with a message that names the key, what
was expected and a fix, for example `Invalid retrieval.llm.provider: expected one of openai,
openai-compatible, ollama, anthropic, google, vertex, got "cohere". Fix: ...`. Inside `llm`,
`embedding`, `egress` and `dimensionValues`, and at the top of the `retrieval` block, an unknown key is an
error that lists the valid ones, so a typo stops the server instead of being ignored.

**Providers.** Each provider is called directly over HTTPS, with no vendor SDK. Failed calls retry
the same way for every provider: a 429, 408, 5xx or timeout is retried up to five times with
jittered exponential backoff and `Retry-After` honoured; a 401, 403 or other 4xx fails at once.
After three failed calls in a row a provider is refused for a minute so a dead endpoint costs a few
timeouts, not one per entity. A reply body that drops or times out after good headers counts as a
network failure and is retried; only a body that arrives whole and is not JSON fails at once. OpenAI's
`gpt-5` and `o`-series models are sent no `temperature`, because the API rejects it; every other
model is sent `0`. Vertex AI errors show the caller the status and a fixed sentence, since its
messages name the project, and a credentials failure shows the fix without the key file path; the
full text stays in the log. JSON replies are read out of code fences, checked, and re-asked once
with the validation error if wrong. Calls, failures, retries, tokens and latency are exported as
`publisher_llm_*` metrics.

| ----------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------- | ------------------------------------------------------------ |
| `openai`, `openai-compatible` | `POST <baseUrl>/chat/completions`                                        | `POST <baseUrl>/embeddings`, up to 512 texts per request            | `Authorization: Bearer`                                      |
| `ollama`                      | same, against the local compatibility API                                | same                                                                | none                                                         |

### Package settings (`retrieval` in publisher.json)

How one package is searched and indexed. It is read when the package loads, so a change takes effect
on reload (and a reload that changes nothing keeps the warm index):

```json
{
  "name": "storefront",
  "retrieval": {
    "fcj": { "perTarget": 30, "listTopK": 15 },
    "sourceSummary": { "enabled": "auto" },
    "prompts": { "judge": "prompts/judge.md" }
  }
}
```

| Key                                                                         | Values                    | Default  | Meaning                                                                                                                                                                         |
| --------------------------------------------------------------------------- | ------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fcj`                                                                       | an object                 | defaults | The engine's own settings, below. Every key is optional.                                                                                                                        |
| `sourceSummary.enabled`                                                     | `auto`, `true`, `false`   | `auto`   | See "Source summaries". `auto`: on when the operator has an LLM configured. `true` with no LLM configured is an error at package load.                                          |
| `prompts.judge`, `prompts.docParts`, `prompts.questions`, `prompts.sourceSummary` | a path inside the package | built in | A file holding the instructions the LLM gets for that step. Absolute paths and anything that resolves outside the package directory (including through a symlink) are rejected. |

An unknown key is an error that names the valid keys, and the package is not served until it is
fixed (HTTP 424, like any unusable publisher.json).

**Keys that no longer do anything.** `engine`, `representation`, `keyphrases`, `refine`, `rerank`,
`sourceMatch`, and the prompts `prompts.keyphrase`, `prompts.refine`, `prompts.rerank` and
`prompts.sourceMatch` belong to the search that this engine replaced. A package that still sets one
loads, whatever the value; the key is ignored (a prompt file it names is not read), and the package's

### The judge

The judge is one chat call per request (one per group with `connect: "clusters"`). It sees the targets
verbatim, and for each target the candidates with their kind, type, source, route and full `#(doc)`
text, rules included. It never sees an access predicate or a field's code (unless `egress.preset` is
`full`). A target the judge picks nothing for comes back in `unresolved_targets`, which is the agent's
signal to ask or to search again.

For a `dimensional_value` target, each candidate field says how its stored values matched (exact, words,
typo or meaning) and their scores. Under the `full` preset it also lists the values themselves, each with
a label, and the judge names the ones it means. A listed value it does not name is left out of the
answer; a value that holds a named one as whole words, and a value past the five it was shown, stay. It
picks nothing when no listed value is the target's value or a form of it (a typo, a different case, an
abbreviation, a synonym). Below `full` it never sees a value, so it names none and every matched value is
returned.

**A search has 90 seconds.** One that runs out of time answers every target in `unresolved_targets`, with a
warning that names a narrower scope to retry with (`scopes[].source`, and for a value
`scopes[].entity_name`). It does not fall back to a cheaper search.

`retrieval.llm.maxCallsPerRequest` (default 20) bounds the chat requests one `get_context` call sends.
It counts HTTP requests to the vendor: a retry after a 429 and the re-ask that repairs a JSON reply each
count. The check runs before each request, so the one that would pass the limit is not sent. Chat
requests made while a person waits retry once, after at most one second (a longer `Retry-After` fails
the call at once); the index build keeps the full retry ladder.

**If the judge fails, the call fails.** When the model cannot be reached, or does not return usable JSON
after the provider layer's retries and its one re-ask, `get_context` returns an error result whose
message names the step, with `retrieval_stage: "judge"` and `retrieval_reason: "llm-stage-failed"`
beside it and no sources. It never answers with an unjudged ranking. `fcj.judge: false` answers without
the judge. A listing runs no LLM step.

**Trace.** A request that carries the header `X-Publisher-Retrieval-Trace: summary` gets a
`retrieval_trace` block with one row per step (`find`, `connect`, `judge`, `page`); `full` adds what each
step kept and why. Starting the server with `PUBLISHER_MCP_TRACE=retrieval` writes the same summary to
the server log, one "Retrieval trace" line per ranked call, and adds nothing to a response. The trace
holds counts and timings, and the header is a diagnostic only: it changes no result.

```json
{
  "retrieval_trace": {
    "engine": "fcj",
    "stages": [
      {
        "name": "judge",
        "status": "ran",
        "ms": 412,
        "in": 1,
        "out": 6,
        "llm_calls": 1,
        "tokens": { "input": 4210, "output": 190 }
      }
    ]
  }
}
```

`status` is `ran`, `skipped` (no LLM, or `fcj.judge: false`) or `failed`.

### Source summaries

A source summary is a paragraph about one source plus a one-line label, written by the LLM at index
time, once, and stored in the `source_summaries` table of `publisher.db`. It is a step of the index
build, so it runs only when the server has an LLM. With `sourceSummary.enabled: "auto"` (the default)
it is on whenever an LLM is configured; `true` with no LLM configured stops the package from loading;
`false` turns it off.

For each source the model gets one call. It is shown the source name, the source's `#(doc)` text (or
`No source docs.`), and the source's fields in four groups, Dimensions, Measures, Views and Joins,
each line `name (type): doc text on one line`. Each joined source is nested under the source with its
own fields, up to three joins deep and 20 joined sources. A source or joined source with more than
200 fields shows 200 of them, spread over the groups, and says `Showing 200 of N fields`. Nothing
else is sent: no code, and no access predicate (every annotation line other than `#(doc)` is removed).
A source with no fields of its own is skipped, as is a source the package hides or locks (it is not an
entity).

The reply is `{"summary": "...", "one_line_summary": "..."}`. The summary is prose that names fields in
backticks; the one-liner is one sentence of at most 120 characters. A source with no `#(doc)` text
must get exactly ``The `<name>` source.``, so the model cannot invent a purpose. A reply that breaks
a rule is shown back to the model once with the reason; if it is still wrong, the step fails.

A source is identified by its model file and its name, so two files that each define `orders` get
their own summary, and a join expands the source in the file it names. One field's `#(doc)` is cut to
500 characters in the prompt, and a prompt over 60,000 characters shows fewer joined sources, then fewer
fields, with a line that says what was left out. For a local model (`llm.provider` `ollama`) the cap
is 6,000 characters: Ollama's default context window (2,048 to 4,096 tokens) cuts a longer prompt
silently, so the summary would be written from a partial field list with no error. If you serve a model
with a larger window you cannot raise this cap; use a hosted model for large packages.

A stored summary is reused until anything the model is shown changes (the source's doc, any field's
name, type or doc, a join, the joined sources' fields), the prompt text or the model, so a restart,
reload or republish of an unchanged package makes no summary call. A change rewrites exactly the
sources it touches: editing a field of `customers` rewrites `customers` and every source that nests it.
`prompts.sourceSummary` replaces the instructions (a file inside the package); the source, its docs,
the field list and the reply format are added by the server.

The step makes one call per source, up to `retrieval.llm.concurrency` at a time, saves each summary as
it returns, and counts against `retrieval.llm.maxCallsPerSync` (sources left over wait for the next
build, which starts on a server restart or after the package's content changes). If a call fails
after its retries and re-ask, the summaries are skipped for that build with a warning in the server log,
keeping the ones already saved; a stored summary that is out of date and could not be rewritten is
deleted, never served.

When a summary is stored for a source, its card's `source_info.one_line_summary` is the model's
one-liner in place of the first line of the source's doc, and the engine searches it as part of the
source's text. A source with no stored summary, and any package or server with summaries off, answers
with the first line of its doc. Listings (a `source` target with no text) are unchanged.

### Dimension value search

A `get_context` target `{"target_type": "dimensional_value", "search_text": "Home Gardeners"}` returns the
string the data stores for what the user typed (`Home Gardeners (In-Season)`) and the dimension that
holds it, as `values[]` on that dimension's entity: `{value, relevance, search_text}`, best first, at most
10 per dimension. Only a `dimensional_value` target searches values. A `dimension` target's text is never
searched as a value: send each value the user named as its own `dimensional_value` target, beside the
`dimension` target for its field. Once you know the field, scope the value search to it with `scopes[].source`
and `entity_name`; an unscoped value search is allowed, but slower, and can return look-alike values from
other fields.

A value target also searches field descriptions by keyword, so a field whose values are not indexed can
still be offered for it. Its card then carries no `values`, and a warning says its values were not checked.

**Which values are searched.** The index build reads the distinct values of `#(index)` dimensions on
ungated sources, and the value lists a doc gives ("one of DTC, B2B, Amazon"), once, through the same
call `execute_query` uses, and matches a phrase against them: the same string, the same after case,
accents, punctuation and spacing, a partial phrase, and a typo (one edit in a word of 4 or 5 letters,
two in a longer one). With an embedding provider and `fcj.valueEmbeddings` they are also matched by
meaning. A dimension no one tagged `#(index)` has no stored values to match.

A read the server refuses because it is at `PUBLISHER_MAX_CONCURRENT_QUERIES`, or one that times out, leaves
that dimension's values out of the build. The index still serves, the server log names the dimension, and
the first question after a one-minute cool-down builds the index again in the background while the old one
keeps answering. Any other failed read (a query error, a missing table) is skipped until the package
reloads, since reading again would fail the same way. A dimension that holds no values is not a failure.

**Access.** A value is data, and a gate applies to it as it does to `execute_query`. A source with
`#(authorize)` or `#(access_filter)` is never read at index time and its values are never embedded. A
`dimensional_value` target that pins one of its dimensions reads the values when asked, through the query
path, with the caller's givens:

- `#(authorize)`: a caller whose givens do not pass gets no values from that source. The source still
  returns, with its dimensions and no `values`, and a warning says the values were withheld.
- `#(access_filter)`: values come only from rows the filter admits. With no givens the gate cannot apply
  and the source is withheld.
- `get_context` takes an optional `givens` argument, read only by this lookup, with the trust `execute_query`'s
  `givens` has: the caller asserts them. See [authorize.md](authorize.md#security-model).

A value search that pins no dimension says which gated sources it skipped.

**Settings.** `retrieval.dimensionValues.enabled` in `publisher.config.json` (default `true`): `false`
makes a `dimensional_value` target answer with the "No index for target_type" warning. The other
`dimensionValues` keys (`maxDimensions`, `maxValuesPerDimension`, `timeoutMs`, `budgetMs`, `cacheTtlMs`)
belonged to the earlier search, are still accepted so an existing file loads, no longer do anything, and
are warned about at startup.

## Semantic ranking for `search_database_schema`

`search_database_schema` searches a configured connection's schema, so an agent can find the
right tables in a database it has never seen and start a model from them. Its ranking is lexical by
default and needs no configuration, no API key, and no network.

Semantic ranking is opt-in and needs **two** variables set, not one: `EMBEDDING_API_KEY` **and**
`EMBEDDING_INDEX_CONNECTION_SCHEMA=true`. That is deliberate. The API key on its own authorises
embedding your own model text, which is already on your disk. A database's table and column names are
your customer's, and turning on semantic `get_context` should not quietly start sending them to
a third party. Setting the second variable is how you say you meant to.

What to know before turning it on:

- What leaves the machine: the schema (or dataset) name, table names, column names, column types,
  and the query strings agents pass to the tool. **Never any row values**: no value from a row is
  returned, logged or embedded. (One nuance, since this section is the one an auditor quotes: for a
  DuckDB connection over CSV or JSON files, DuckDB's own type sniffer reads the head of the file to
  infer column types. That inference happens in your warehouse and only its column names and types
  leave; no cell value is returned or sent anywhere.) Point `EMBEDDING_API_BASE` at a local OpenAI-compatible server
  (Ollama, vLLM) to keep even the names on-machine.
- What it buys you: lexical ranking only matches tables that share words with the question, so
  "website visits" does not find `web_session_events` and "newsletter blasts" does not find
  `marketing_email_campaigns`. Embedding similarity matches those by meaning. On the eval fixture,
  lexical scores 6/10 at recall@3, missing exactly the four questions that share no words with
  their table.
- Storage: schema vectors are held **in memory only**, keyed per connection and schema and
  invalidated by a fingerprint over the tables and their columns. The key is the environment,
  connection and schema (plus the package, for the per-package `duckdb` sandbox). At most a few
  schemas are held at once, least-recently-used evicted. They are not written to
  `publisher.db`, so a restart re-embeds a schema the first time it is searched again.
- Failure behavior: if the endpoint is down, times out, or rejects the key, ranking falls back to
  lexical (with a warning in the server log) and retries after a cool-down. A schema with more than
  5,000 tables is not embedded and stays lexical; lexical is not the cheaper branch, it just
  needs no provider. Its index is built once per schema and cached, so the cost lands on the first
  search after a schema changes rather than on every search. A search response carries a `ranking` field (`"semantic"` or `"lexical"`) so you can tell which
  one answered; a plain listing does no ranking and carries none.
- To measure the difference yourself, including the A/B against the lexical baseline, see the eval
  script header in `packages/server/scripts/schema_search_eval.ts`.

| `malloy_package_load_compile_duration{status}`, `_schema_fetch_duration{status}`, `malloy_package_load_schema_fetches` | Histograms | Inside the package-load worker: compile time, including the render-tag results, companions and build plan it prepares for the main thread; time waiting on proxied schema fetches; and how many fetches there were.                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `publisher_package_load_phase_duration_ms{phase}`                                                                      | Histogram  | Each stage of a load that succeeded, one sample per stage per load: `worker` (the worker's job as the main thread waits for it), `hydrate` (building the served models from its output and checking their persist names), `render_validation`, `discovery` and `lint` (the package's reports), `build_plan` (applying the plan the worker derived, or deriving it here when the worker left it at its soft deadline; absent when it failed) and `total` (the whole load). Every stage but `worker` runs on the main thread. Recorded by package loads only; a reload (a manifest rebind or a materialization refresh) records none. |

`total` minus `malloy_package_load_duration` is the part of a load after its models are validated
(discovery, lint and the build plan), which the older metric does not see. Every stage is wall-clock
time. The main-thread stages yield to other requests every 10 ms, so they include the time spent
serving them: a stage grows with traffic as well as with package size, and is read alongside the
server's request rate. None of them measures main-thread CPU.

## Server settings (top level of `publisher.config.json`)

Settings that describe the server itself, rather than an environment, sit at the top level of the
config, beside `environments`:

| Field | Default | Meaning |
| --- | --- | --- |
| `frozenConfig` | `false` | `true` makes the server read-only through the API: every write to environments, packages, connections, the theme and saved reports answers `403`. Reported on `GET /status`. |
| `servingApiEnabled` | `true` | The main API and MCP, and the environments they serve. `false` runs only the admin API: it requires `PUBLISHER_ADMIN_PORT`, loads no environments (so watch mode is absent), and refuses to start if the config declares any. |
| `adminApiEnabled` | `true` | Whether the admin API may run; it still starts only when `PUBLISHER_ADMIN_PORT` is set. `false` refuses to start if `PUBLISHER_ADMIN_PORT` or `PUBLISHER_ADMIN_CATALOG_DATABASE` is set. |
| `theme` | _none_ | The server's default theme ([theming.md](theming.md)). |
| `mcp` | _none_ | MCP settings ([below](#mcp-settings-mcp)). |
| `retrieval` | _none_ | Retrieval settings for `get_context` ([above](#semantic-retrieval-for-get_context)). |
| `environments` | `[]` | The environments to serve. |

`servingApiEnabled` and `adminApiEnabled` can also be given as `PUBLISHER_SERVING_API_ENABLED` and
`PUBLISHER_ADMIN_API_ENABLED`, or as `--[no-]serving-api-enabled` and `--[no-]admin-api-enabled`; a flag wins
over the variable, and the variable over the file. In the file the value is `true` or `false`, or a
`${VAR}` reference; a variable takes `true/false`, `1/0`, `yes/no` or `on/off`. Any other value fails
startup, and so does both `false`. A server that serves other people's environments sets
`"adminApiEnabled": false`, and the process holding the admin API's catalog credential sets
`"servingApiEnabled": false` ([ducklake.md](ducklake.md), "Running it on its own").

## MCP settings (`mcp`)

The `mcp` block of `publisher.config.json` holds settings for the MCP server. It has one key:

```json
{ "mcp": { "includeHiddenFilesAndSources": true } }
```

- `includeHiddenFilesAndSources` (boolean, default `false`): offer the `includeHiddenFilesAndSources`
  parameter on MCP `execute_query`. With it, a query can run the files and sources a package's
  `index.malloy` hides, so an author can test them before publishing them. It never bypasses
  `#(authorize)` or `#(access_filter)`. Leave it off on a server that answers questions: off removes
  the parameter from the tool's schema, so an agent is never offered it. The REST parameter of the
  same name does not depend on this setting.
- The value is read once, at startup. Restart the server after changing it.
- A value that is not a boolean, or an `mcp` that is not an object, is warned about and ignored.

## Startup signals

The server prints one line to stderr when it is ready, so a script can wait for it instead of polling
`/api/v0/status`:

```
PUBLISHER_READY url=http://localhost:4000 mcp=http://localhost:4040 environments=1 packages=3 load_errors=0
```

- `load_errors` counts configured packages and environments that failed to load. When it is not 0,
  `/api/v0/status` names each one under `.loadErrors`.
- `url=` reads `localhost` when the server binds every interface (the default); a configured `--host`
  shows as itself.
- If initialization fails, `PUBLISHER_INIT_FAILED` is printed in its place. A startup failure outside
  initialization — a port already in use, say — crashes without either token.
- On a Node older than 20 the server prints `PUBLISHER_UNSUPPORTED_NODE required=>=20 detected=<version>`
  and exits non-zero before binding anything, so a script waiting on `PUBLISHER_READY` fails fast
  instead of hanging. Every `@malloydata/*` dependency shares that floor; older runtimes are untested
  and have failed in ways that never mention Node.
