# Persisting a `#(access_filter)`-gated source

A gated source **can** be persisted, on either tier but only in one shape, and the thing to be careful about is not refused by anything - you have to decide it.

- **`#@ preaggregate` always refuses a gated source**, naming it. The build skips a refused source, records it on the run (`metadata.refusedSources`), and builds the rest of the package. A run fails on a refusal only when every authored source it targeted was refused, or when `sourceNames` named this one; a refused rollup never fails it. (`#@ preaggregate` stores a rollup Publisher derives from a measure you annotated with a grain, rather than a source you wrote.) A rollup also groups *across* the gated column, so it could not be row-filtered afterwards even in principle.
- **A `#@ persist`, colocated or `storage=`, is admitted** when the gate is the entry point's **own row filter** (or an `#(authorize)` lock): declared on the persisted source itself, and classified as a row filter. Both tiers follow the same rule (so does `#(materialize)`): the table holds every caller's rows and the gate is re-applied on every read through Publisher. (`#@ persist storage=<name>` materializes into a separate registered storage destination and serves from there, rather than building in the source's own connection.) **A `storage=` table puts those rows, ungated, at rest in the destination**, where anyone with direct access to the destination reads every row; tell the author before choosing that tier for a gated source, and make sure no connection a model can name reaches the destination (its catalog, schema or data path): stored tables are named predictably, so any package could read the gated rows through it. It is refused in three cases: the gate is reached only through a join, it does not classify as a row filter at all, or the persisted source inherits it from a source it derives from or extends (`source: mine is gated -> { ... }`, `gated extend { ... }`, across imports or two hops away). A table of an inherited gate would hold every caller's rows, and the served copy, which reads the table in place of the source that declares the gate, cannot apply the gate to it, so every query would answer live anyway: it is not built. Declare the gate on the persisted source itself to serve it from a table.

**What to be wary of.** Persisting does not weaken the gate: it changes only where rows are read FROM, and the gate still runs live on every query as that query's own `WHERE`, so filtered rows come back filtered. What freezes is the **column the gate filters on**. A row whose access decision changes - it changes owner, say - keeps being served under its OLD decision until the next rebuild. That is a stale *access decision*, not merely stale data, and nothing raises an error.

**None of this is needed for the gate to work.** It is enforced live on every query either way; what needs a bound is how long a *stale* decision can survive. Of the three controls that look like that bound, only the first is:

- **`freshness.window="24h"` with `freshness.fallback="live"` is the bound** (`reference/refresh.md`). The serve path re-checks freshness per query, so once the artifact ages past the window it drops out of the serving set and the query recomputes live, correctly filtered - whether or not a rebuild ever lands. Three details decide whether you actually get that. **`fallback` must not be `stale_ok`**: under `stale_ok` a stale artifact keeps being served, which voids the bound (`live` and `fail` both bound it today). Window and fallback resolve *independently, per field*, across the source, model-file and package layers, so a package-level `stale_ok` silently defeats a window you set on the source. Prefer the **per-source** spelling `#@ persist name="..." freshness.window="24h" freshness.fallback="live"` over the package-wide `materialization.freshness` key: the gated source is what needs the bound, and setting it package-wide forces every other persisted source to recompute once stale too. And **a content-identical sibling shares the artifact, so it shares the window**: reuse is keyed on the content-addressed `sourceEntityId`, which folds the connection and the SQL but *not* the source name, so two persist sources whose bodies compute the same SQL, with the same `name=` or none, resolve to one table carrying one freshness policy (different `name=`s are different tables). A host that folds the siblings' policies keeps the tightest window any of them declares - a sibling declaring nothing cannot loosen yours, and yours pulls that sibling's reads off the table once it lapses - and keeps the bounding fallback, so a sibling's `stale_ok` cannot void your bound either. If two sources need genuinely different windows, give them different `name=`s or genuinely different SQL.

  Both of those are properties of the **host** that assembles the manifest, not of the annotation: the publisher reports freshness per source and does no folding itself. Where the host does not fold, which sibling's policy reaches the wire is unspecified; a host that folds does so when it next publishes a version's manifest, not retroactively to manifests already distributed - so you can declare the window correctly and not have it in force yet.
- **A cron alone is not a bound.** A failed build or a stopped scheduler leaves the source serving its old decisions indefinitely. `freshness` and `schedule` are mutually exclusive; for a gated source, take the window.
- **`refresh="incremental"` does not bound revocation.** The delta only re-reads rows in `[covered_through, frontier)`, so a row that changes owner *without its watermark advancing* is never re-read - while the entry still reports an advancing `coveredThrough` and reads as healthy. Only a full rebuild recomputes the gating column.

**The window binds on a standalone server and under a control plane alike.** A standalone run stamps the declared window and the table's `dataAsOf` on the manifest it commits, as a control plane stamps the manifest it distributes, so the table ages out per query either way. Under a control plane, the control plane's manifest decides: what it stamps applies whatever the model declares.

When recommending `#@ persist` on a gated source, pair it with a freshness window and say out loud what staleness the author is accepting. A gated source with neither a window nor a full-rebuild cadence has no bound on how long a revoked row keeps being served.
